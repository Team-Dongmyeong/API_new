# 채용공고 UI/UX 설계 작업 진행 및 향후 계획 정리 보고서

## 1. 작업 목적 및 진행 배경
- **목적:** 잡코리아/사람인 채용공고 Open API가 아직 발급되지 않은 상황에서, 프론트엔드(UI/UX)를 먼저 완성하고 더미데이터로 전체 화면·기능 동작을 사전 검증.
- **진행 환경:** Vite + React + Tailwind CSS
- **대상 파일:** `Jobs.jsx`, `mocks/jobs.js`, `constants/jobCategories.js`, `context/PreferenceContext.jsx`, `components/PreferenceQuiz.jsx`, `components/Header.jsx`, `pages/app/MyPage.jsx`, `pages/app/AppLayout.jsx`

## 2. 작업 진행 단계 및 상세 과정

### 2-1단계: 채용공고 페이지 기본 UI 구성 (`Jobs.jsx`)
- 잡코리아 "스마트픽" 스타일을 참고해 히어로 배너 → 키워드/지역 검색바 → 카테고리 필터 칩 → 공고 카드 리스트 순으로 레이아웃 구성.
- 참고 자료의 보라·파랑 계열 배너 색상 대신, 서비스 브랜드 컬러(ink → coral 그라데이션)로 재구성.

### 2-2단계: 지역 필터 구조 설계 및 버그 수정
- **최초 구성:** 특별시/광역시/도 단위로 `<optgroup>` 그룹핑.
- **발생 이슈:** `label` 속성이 누락되면서 `<optgroup label={undefined}>`가 빈 행으로 렌더링됨.
- **1차 수정:** `label` 복구.
- **최종 결정:** 그룹 구조 자체를 제거하고, 광역시 7개 + 도 단위를 그룹 없이 하나의 평면 리스트로 재구성.
- **부가 수정:** 지역의 `value`(필터링용 축약형, 예: `서울`)와 `label`(표시용 정식 명칭, 예: `서울특별시`)을 분리 — 정식 명칭만 있을 경우 `job.location`(예: `서울 강남구`) 문자열과 매칭이 안 되는 필터링 오류가 있어 사전에 발견해 수정함.

### 2-3단계: 더미 채용공고 데이터 대량 생성
- 대분류 5개(IT/SW, 디자인, 공공·복지, 식·음료, MD/상품기획), 세부직무 37개 확정.
- **범위 확정:** 세부직무당 10건 기준 총 370건 생성(지역별 10건이 아닌, 전체 세부직무 기준 10건으로 범위를 명확히 함).
- Python 스크립트로 기업명/태그/지역/마감일 풀(pool)을 카테고리별로 다르게 순환시켜, 완전 무작위가 아니라 재현 가능한 방식으로 실제 공고처럼 보이는 데이터 생성.
- `Jobs.jsx`에서 데이터를 분리해 `mocks/jobs.js`로 독립 — 배포 시점에 API 응답으로 교체하기 쉬운 구조로 정리.

### 2-4단계: "선호 추천 분야" 실시간 공유 아키텍처 설계
- **요구사항:** 적성 검사 결과 60% + 채팅 분석 결과 40%를 합산한 값이, 채용공고 스마트픽·마이페이지 등 여러 화면에서 동시에 실시간 반영되어야 함.
- **구현:** React Context API(`PreferenceContext.jsx`)로 전역 상태 관리.
- **핵심 설계 포인트:**
  - **Provider 위치:** `AppLayout.jsx`에서 `key={pathname}`으로 매번 리마운트되는 영역 바깥에 `PreferenceProvider`를 배치 — 페이지 이동 시 값이 초기화되는 문제를 사전에 방지.
  - **`toVector()` 헬퍼:** 카테고리 문자열 하나만 전달돼도(100% 신뢰도로 간주) 동작하고, 이미 계산된 확률 분포 객체(`{ 'IT/SW': 0.6, '디자인': 0.4 }`)가 와도 그대로 처리 — 추후 실제 모델이 신뢰도 분포를 반환하게 되어도 이 파일을 손댈 필요가 없도록 설계.
  - **`hasPreferenceData`:** 검사·채팅 모두 미응답(전부 0점)인 상태와, 실제 진단 결과가 나온 상태를 구분해서 화면에 "미설정"을 정직하게 보여줄 수 있게 함.
  - **`resetPreference()`:** 진단 결과를 초기화하는 기능.

### 2-5단계: 진단하기 임시 테스트 기능 구현 (`PreferenceQuiz.jsx`)
- 목적: 실제 GPT+RAG 채팅, KcELECTRA/SBERT 적성 검사가 아직 연동되지 않은 상태에서 "검사 60%" 반영 로직만 수동으로 확인.
- 5개 질문 × 선택지 5개, 각 선택지가 대분류 5개와 1:1로 대응하는 임시 진단 구성.
- 응답 결과를 카테고리별 비율 벡터로 계산해 `setTestResult`에 전달.
- 특정 페이지에 종속되지 않도록 독립 컴포넌트로 분리해 여러 화면에서 재사용 가능하게 구성.

### 2-6단계: 진단하기 UI 배치 반복 수정
아래 표와 같이 세 차례에 걸쳐 배치 방식을 수정함 (자세한 비교는 5장 참고).

| 시도 순서 | 배치 방식 |

| 1차 | 마이페이지 프로필 탭 하단 인라인 카드 |
| 2차 | 마이페이지 오른쪽 슬라이드 패널 + 초기화 기능 추가 |
| 3차 | 마이페이지 자체 헤더의 박스 + 화면 중앙 모달 |

### 2-7단계: 마이페이지 연동 (`MyPage.jsx`)
- 기존에 자유 텍스트로 입력하던 "선호 추천 분야" 입력 필드를 제거하고, `usePreference()` 훅으로 실시간 값만 읽어와 표시하도록 변경.
- "내 정보" 카드에 값 표시 + "초기화" 버튼 배치.
- 진단하기 박스/모달 관련 코드(상태, 핸들러, JSX)는 전부 `Header.jsx`로 이전하고 마이페이지에서는 제거.

### 2-8단계: 전역 헤더(`Header.jsx`)에 최종 배치
- 로그인 상태일 때만 "test22님" 이름 좌측에 알약 모양의 "진단하기" 박스 노출(진단 전엔 "진단하기", 진단 후엔 결과 카테고리명).
- 클릭 시 화면 정중앙에 진단 모달이 뜨고, 배경 클릭/Esc로 닫힘.
- `usePreference()`가 `PreferenceProvider`로 감싸이지 않은 화면(로그인 전 랜딩 페이지)에서 호출돼도 에러 없이 안전한 기본값(noop)을 반환하도록 사전에 수정 — Header가 로그인 전/후 화면 모두에서 재사용되는 공용 컴포넌트이기 때문.

## 6. 앞으로의 작업

### 6-1. 적성 검사(KcELECTRA/SBERT) 고도화
- **현재 상태:** 5문항짜리 임시 진단(`PreferenceQuiz.jsx`)으로 "검사 60%가 반영되어 화면이 실시간으로 바뀐다"는 구조만 검증된 상태. 실제 심리·적성 척도에 기반한 문항이 아님.
- **필요 작업:**
  - 실제 적성 검사 문항 설계(문항 수, 어떤 심리척도·직무적성 이론에 기반할지, 5개 대분류 각각을 어떤 질문으로 변별할지).
  - KcELECTRA/SBERT 모델이 사용자 응답(선택형 또는 서술형 텍스트)을 입력받아 5개 대분류(또는 37개 세부직무까지) 확률 분포를 출력하도록 모델 연동/파인튜닝.
  - 모델 출력값을 `PreferenceContext`의 `toVector()`가 기대하는 `{ 카테고리: 비율 }` 형태로 변환하는 어댑터 함수 작성 (현재는 `PreferenceQuiz`가 이 역할을 임시로 대신하고 있음).
  - 검사 결과 신뢰도가 낮거나 애매할 때의 UX 처리 방안 설계 (예: 상위 2개 후보 동시 노출, "재검사 추천" 안내 등).
  - 문항 수가 늘어날 경우 모달의 높이/스크롤/진행률 표시(예: "3/15 완료") 등 UI 재설계 필요.

### 6-2. 채팅(GPT+RAG)과의 결합 방식
- **현재 상태:** `PreferenceContext`에 `setChatResult()` 함수 자체는 만들어 40% 가중치를 받을 준비가 되어 있지만, 실제로 이 함수를 호출하는 채팅 화면 로직은 아직 없음.
- **필요 작업 및 검토할 이슈:**
  - GPT+RAG 파이프라인이 대화 내용에서 관심 직무 키워드·감정 상태를 추출한 뒤, 그 결과를 어떤 형식(카테고리 하나? 확률 분포?)으로 프론트엔드에 넘길지 API 응답 스펙 정의.
  - 대화 도중 실시간으로 `setChatResult`를 계속 갱신할지, 대화가 일정 턴 수 이상 진행되거나 세션이 종료된 시점에 한 번에 반영할지 정책 결정 필요.
  - **가중치 재조정 문제:** 현재 로직은 검사 또는 채팅 중 한쪽 결과가 없으면 해당 항목이 0점 처리되어, 검사만 받고 채팅을 아직 안 한 사용자는 사실상 "60%만 반영되고 나머지 40%는 버려지는" 상태가 됨. 한쪽만 존재할 때 나머지 가중치를 어떻게 재분배할지(예: 검사만 있으면 검사 100% 취급) 검토 필요.
  - 채팅이 **직무 매칭 목적**으로 흐를 때와 **정서 지지(감정 상담) 목적**으로 흐를 때를 구분해서, 감정 지지 대화 내용으로는 선호 추천 분야를 갱신하지 않도록 하는 필터링 로직 필요.
  - 실제 채팅(Chat) 페이지에서 `usePreference().setChatResult(...)`를 호출하는 지점 구현.

### 6-3. 실제 API(사람인) 연동 시 마이그레이션
- `mocks/jobs.js`의 `DUMMY_JOBS`를 실제 API 응답으로 교체하는 절차 정리.
- API 응답 필드명이 현재 프론트엔드가 기대하는 필드(`company`, `title`, `subJob`, `location`, `category`, `type`, `tags`, `deadline`)와 다를 경우를 대비한 매핑(어댑터) 함수 작성.
- API 호출 실패·로딩 상태에 대한 UI 처리(스켈레톤 UI, 에러 메시지 등) 추가 — 현재는 더미데이터라 항상 즉시 렌더링되는 상태라 이 부분이 아직 없음.

### 6-4. 기타 후속 UX 작업
- 채용공고 상세 페이지 설계.
- 공고 스크랩/지원 기능.
- "왜 이 분야가 추천됐는지"를 보여주는 진단 결과 상세 설명 화면.
- 모달 접근성 보완 — 현재는 배경 클릭/Esc 닫기만 구현되어 있고, 키보드 포커스 트랩(Tab 이동이 모달 밖으로 빠져나가지 않게 하는 처리)은 아직 미구현.

## 7. 결론
현재까지는 잡코리아/사람인 API 미발급 상태를 고려해, 더미데이터 기반으로 채용공고 화면과 "선호 추천 분야 실시간 반영" 아키텍처를 먼저 완성했다. 검사(60%)·채팅(40%) 합산 구조 자체는 검증됐지만, 실제 값을 채워 넣는 두 축인 **적성 검사 모델 연동**과 **채팅 분석 결과 연동**이 다음 단계의 핵심 과제이며, API 발급 완료 시 더미데이터를 실제 응답으로 교체하는 작업이 그 뒤를 잇는다.
