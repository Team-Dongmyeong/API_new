## 0단계. 회의에서 먼저 정해야 할 것 (매핑 최종 확정)

`37개 세부직무-NCS 최종 매핑안.md`를 같이 보면서, ⚠ 표시된 7개 항목을 팀이 눈으로 보고 결정해야 함. 이게 끝나야 다음 단계(능력단위 수집)로 넘어갈 수 있음 — 세분류 코드가 확정돼야 그 코드로 API를 호출할 수 있기 때문.

### 회의 안건 체크리스트

- [ ] **QA** — NCS에 QA/테스트 전용 세분류가 없음. "02.응용SW엔지니어링"에 잠정 배치된 채로 갈지, 아니면 QA는 아예 별도 문항 없이 다른 세분류(예: 응용SW엔지니어링) 문항을 그대로 쓸지 결정.
- [ ] **게임개발자** — "게임프로그래밍"이라는 세분류가 실제로 없음. "02.응용SW엔지니어링"(개발 관점)으로 갈지, 08/03/02의 "05.게임콘텐츠제작"(콘텐츠 관점)으로 바꿀지 결정. → **판단 기준**: 우리 서비스가 겨냥하는 "게임개발자"가 프로그래밍 중심인지, 기획/콘텐츠 제작도 포함하는 넓은 의미인지 먼저 정의할 것.
- [ ] **앱개발자** — "모바일앱개발" 항목이 없어 "응용SW엔지니어링"으로 통합됨. 백엔드/웹개발자와 세분류가 겹치는데 괜찮은지 확인.
- [ ] **광고 디자이너 / 편집 디자이너** — 디자인 소분류 안에 전용 항목이 없음. "시각디자인"으로 통합할지, 광고 디자이너만 08/03/02의 "04.광고콘텐츠제작"(콘텐츠마케터와 동일 세분류)으로 옮길지 결정.
- [ ] **사회복지사** — 세분류 후보 5개(프로그램운영/일상생활지원/면담/사례관리/자원봉사관리) 중 하나만 쓸지, 여러 개를 합쳐서 쓸지 결정.
- [ ] **셰프·주방장 / 요리사 / 조리사** — 조리 분야(한식/양식/중식/일식) 구분이 세부직무명에 없어서 셋 다 "공통직무"로 잠정 배치됨. 이 세 직무를 이대로 둘지, 아니면 애초에 37개 세부직무 목록에서 이 셋을 하나로 합치거나 분야별로 재정의할지까지 검토.

### 회의 후 할 일

- [ ] 위 결정 사항을 반영해서 `fetch_ncs.py`의 `JOB_NCS_MAP`과 최종 매핑 표를 업데이트
- [ ] 세분류가 바뀐 항목이 있으면 그 항목만 스크립트 재실행해서 `ncs_subd_candidates.json` 최신화
- [ ] **37개 세부직무 ↔ NCS 세분류 매핑 최종 확정** (이걸로 "1단계: 매핑"이 완전히 끝남)

## 1단계. NCS005/006 파라미터 확인 (재료 수집 준비)

능력단위·능력단위요소를 가져오려면 NCS005(능력단위분류코드 조회), NCS006(능력단위요소 조회) API를 호출해야 하는데, 이 두 오퍼레이션의 정확한 요청 파라미터명이 아직 확인이 안 됐음. NCS002(중분류)·NCS004(세분류) 때와 똑같은 방법으로 확인하면 됨.

### 체크리스트

- [ ] data.go.kr 마이페이지 → "한국산업인력공단_NCS 기준정보 조회" API → 활용신청 상세보기 진입
- [ ] "상세기능정보" 탭에서 **NCS005(능력단위분류코드 조회)**의 "요청변수(Request Parameter)" 표 스크린샷 캡처
- [ ] 같은 방법으로 **NCS006(능력단위요소 조회)**의 요청변수 표도 스크린샷 캡처
- [ ] 스크린샷 두 장을 보내주면, 내가 `fetch_ncs.py`에 정확한 파라미터명으로 반영

> 참고: NCS002는 `NCS_LCLAS_CD`, NCS004는 `NCS_LCLAS_CD/NCS_MCLAS_CD/NCS_SCLAS_CD` 방식이었으니, NCS005도 아마 `NCS_SUBD_CD`(세분류 코드)를 받는 비슷한 패턴일 가능성이 높음. 다만 추측만으로 코드를 짜면 또 `NO_MANDATORY_REQUEST_PARAMETER_ERROR`가 날 수 있어서, 이번에도 스크린샷으로 확인하고 가는 게 제일 빠름.

## 2단계. 능력단위 · 능력단위요소 수집 (재료 수집)

0단계에서 확정한 세분류 코드마다 능력단위 목록(NCS005) → 능력단위요소 목록(NCS006)을 순서대로 조회해서, 문항의 원재료가 될 "~할 수 있다" 형태의 문장들을 전부 모으는 단계.

### 체크리스트

- [ ] `fetch_ncs.py`에 NCS005/006 호출 로직 추가 (지금 있는 `call_ncs()` 함수 그대로 재사용 가능)
- [ ] 확정된 세분류 코드 전체(30여 개)에 대해 순서대로 NCS005 호출 → 능력단위 목록 확보
- [ ] 각 능력단위마다 NCS006 호출 → 능력단위요소(세부 문장) 확보
- [ ] 전체 결과를 `ncs_elements.json` 같은 파일로 저장 (지금 `ncs_subd_candidates.json` 만든 것과 같은 방식)
- [ ] 세분류당 능력단위요소가 몇 개씩 나오는지 개수 확인 — 너무 적으면(3개 이하) 문항 수가 부족할 수 있으니 상위 소분류 단위로 합쳐서 보완할지 미리 점검

## 3단계. 문항화 (능력단위요소 → 설문 문항)

이 단계부터는 API가 아니라 **팀이 직접 손으로 하는 작업**이야. 능력단위요소 원문("~을 할 수 있다" 식의 문장)을 자기보고식 설문 문항("나는 ~하는 것을 좋아한다/자신 있다")으로 재작성하는 단계.

### 체크리스트

- [ ] 문항 톤/형식 통일 규칙 정하기 (예: 전부 "나는 ~을 좋아한다" 5점 척도로 통일할지, 직무마다 다르게 할지)
- [ ] 세분류(직무)당 문항 개수 정하기 (예: 직무당 3~5문항 × 37개 직무 = 총 문항 수 결정)
- [ ] 능력단위요소 원문을 팀원끼리 나눠서 문항 초안 작성
  - 예시: "고객 요구사항을 분석하여 요구사항 정의서를 작성할 수 있다" → "나는 다른 사람의 요구를 정리해서 문서로 만드는 일이 편하다"
- [ ] 저작권 문제 없도록, 원문 표현을 그대로 베끼지 않고 반드시 재구성했는지 서로 교차 확인
- [ ] 초안 1차 완성본을 팀 전체가 리뷰

## 4단계. 문항-직무 태깅

작성한 문항마다 "이 문항에 응답하면 어떤 직무(혹은 대분류)에 가중치를 줄지"를 태깅하는 단계. 기존 `PreferenceQuiz.jsx`의 선택지별 `category` 태깅 구조와 똑같은 패턴이라, 코드 확장은 어렵지 않음.

### 체크리스트

- [ ] 문항 하나가 세부직무 1개에만 연결되는지, 여러 개에 걸쳐 태깅될 수도 있는지 규칙 정하기
- [ ] 태깅 결과를 표/JSON으로 정리 (문항ID → 세부직무명 매핑)
- [ ] `PreferenceQuiz.jsx`의 `QUIZ_QUESTIONS` 구조를 5개 대분류 기준에서 37개 세부직무 기준으로 확장할지, 대분류는 유지하고 세부직무는 내부적으로만 세분화할지 설계 방향 결정

### 체크리스트

- [ ] 채팅 상담 분석 결과(40%)도 세부직무 단위로 나올 수 있는지 채팅 담당 팀원과 협의 (지금은 대분류 단위 가정으로 설계돼 있음)

## 결론 — 왜 이 방식으로 하는지, 지금 어디까지 왔는지

### 1. 이미 완성된 설문지를 그대로 가져오는 건 왜 불가능한가

워크넷 직업선호도검사, 커리어넷 진로심리검사, NCS 직무능력진단처럼 이미 만들어진 검사를 그대로 가져와서 채점 로직만 우리 서비스에 맞게 바꾸는 방법을 제일 먼저 검토했는데, 세 가지 이유로 폐기함.

| 사유 | 상세 내용 |
|---|---|
| 저작권 문제 | 표준화된 검사 문항은 대부분 저작물로 보호됨. 채점 로직만 바꾸고 문항 문장을 그대로 쓰는 것도 "그대로 베낀 것"에 해당해 저작권 침해 소지가 있음 |
| 기술적 차단 | 실제로 ncs.go.kr 같은 공식 검사 페이지를 프로그램으로 가져오려 시도했을 때 `robots.txt`로 접근 자체가 차단되어 있는 걸 확인함 — 스크래핑을 명시적으로 금지하는 정책 |
| 논문 특성상 문제 | 이 프로젝트는 졸업논문이고 "직접 설계한 진단 알고리즘"이 핵심 기여점임. 기존 검사를 그대로 가져오면 독창성이 없어져서 표절 시비로 이어질 수 있고 심사에도 불리함 |

결론: 완성된 설문지를 그대로 가져오는 방식은 처음부터 배제하고, 진단 알고리즘 자체를 우리가 직접 설계하는 방향으로 감.

### 2. 그럼 지금 하고 있는 건 "스크래핑"이 아닌가

지금 `fetch_ncs.py`로 하고 있는 작업은 위에서 말한 "금지된 스크래핑"과는 성격이 완전히 다름.

- **가져오는 대상이 다름**: 저작권이 있는 "완성된 검사 문항"을 몰래 긁어오는 게 아니라, 국가가 공식적으로 만들어서 공개한 **직무 분류 체계 원자료**(NCS 세분류·능력단위·능력단위요소 — "이 직무는 이런 일을 할 수 있어야 한다"는 사실 정보)를 가져오는 것.
- **가져오는 방법이 다름**: 접근이 차단된 페이지를 억지로 긁는 게 아니라, 공공데이터포털에 정식으로 활용신청을 하고 승인받은 API(한국산업인력공단_NCS 기준정보 조회)를 정해진 방식대로 호출하는 것. 이 API는 애초에 개발자가 이렇게 갖다 쓰라고 국가가 공식 제공하는 데이터임.
- **결과물의 성격이 다름**: API로 가져온 원문("~할 수 있다" 형태의 사실 문장)을 그대로 설문 문항으로 쓰는 게 아니라, 팀이 직접 자기보고식 문항("나는 ~하는 것을 좋아한다/자신 있다")으로 재작성하는 "문항화" 과정을 반드시 거침. 그래서 최종 결과물은 기존 검사를 베낀 게 아니라 우리가 직접 설계한 오리지널 진단 도구가 되고, 논문에서 요구하는 독창성도 확보됨.

정리하면: "완성된 설문지 스크래핑"은 불가능해서 배제했고, 지금 하는 "NCS 원자료 API 수집"은 그 대안으로 선택한, 저작권·정책상 문제 없는 정식 경로임.

### 3. 이 방식으로는 어떻게 진행해야 하는가 (전체 흐름)

1. 37개 세부직무를 NCS 세분류 코드에 매핑
2. 그 세분류마다 능력단위·능력단위요소를 API로 수집
3. 능력단위요소 문장을 팀이 손으로 설문 문항으로 재작성 (문항화)
4. 문항마다 어떤 직무에 가중치를 줄지 태깅
5. 응답을 직무별 점수로 환산하는 채점 로직 설계
